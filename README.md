Bilingual portfolio of **Sebastián López Osorno**, backend and integration developer, live at
[sebastianlopezo.page](https://sebastianlopezo.page). This repository is its Astro and SolidJS edition, migrated from
the React one with the same pages, content, design, tests and deployment (
see [Migration from React](#migration-from-react)).

- Pages generated by Astro in English and Spanish (`/en`, `/es`), whose interactive parts are SolidJS islands.
- One general profile plus five role views that reorder and emphasize the same content.
- Thirty-two project pages: five full case studies (integration platform, SmartPot, GoPoli, MarTech, email
  signatures) and twenty-seven lighter pages for the other work, product and education projects, each with its
  achievements, architecture, figures and repositories, its decisions told as a problem and a solution in small tabs,
  and links to the job, program, organization and certifications behind it; a projects index by category and a
  filterable archive of public repositories.
- A page for every job, program, certification and GitHub organization (4, 5, 29 and 10, each collection with its
  index): titles and role changes, a timeline built from the facts that filters by kind and groups by year, projects,
  recommendations, courses, each certificate as its issuer publishes it and where it shows in the work, and the
  commits in each organization.
- Shareable role links that can be locked so the visitor stays on that view.
- Complete SEO per page: titles and descriptions that fit a search result (a build test checks them), canonical and
  `hreflang` links, an Open Graph image for every project, job, program, certification and organization, JSON-LD with
  each project's screens and each certificate, a sitemap with image entries that dates each page by the day its
  text last changed, robots, and an `llms.txt` that maps the English pages, the resumes and the contact for language
  models from the titles and descriptions the pages already carry.
- An interactive journey: a transit-style SVG map of education and work from 2019 to the 2030 goals, a capability
  heatmap per year, a focus radar of what is core, growing, exploring or paused, and the next steps (data science
  specialization, cybersecurity master's) tied to the UN 2030 Agenda goals.
- A client-side profile assistant that answers from the portfolio content, with no AI service: about thirty kinds of
  question (each job, program and project by name, certifications by topic, services, reasons to hire, GitHub
  activity, availability), each answer linking to the page that tells more, with follow-up questions and a catalog of
  the 42 questions it was built for.
- Dark design system with WCAG AA contrast checked in CI.
- Motion the browser draws from CSS: parts that rise as they enter the screen, a reading progress bar on the header,
  pages that fade into each other and figures that count up once, all of it off for a reader who asks for less motion.
- Shipped as a ~30 MB unprivileged nginx image on GHCR and deployed with Docker Compose.

Lighthouse CI holds every build to 100 in accessibility and SEO, 95 or more in best practices and warns under 90 in
performance (`lighthouserc.json`); the **Production Checks** workflow runs it again against production after every
deploy. Performance varies with the runner.

## Getting started

Requirements: Node.js 22.18 or newer and pnpm 10 (`corepack enable`).

```bash
pnpm install
pnpm dev        # http://localhost:8080
pnpm build      # prerendered site in dist/
pnpm preview    # serves dist/ with the same rules as production on http://127.0.0.1:4173
```

| Script                         | Purpose                                                                                                                                              |
|--------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| `pnpm lint` / `pnpm typecheck` | ESLint and TypeScript checks                                                                                                                         |
| `pnpm test`                    | Unit tests (content parity, paths, role views, SEO, assistant)                                                                                       |
| `pnpm test:dist`               | Checks the built pages, crawler files and size budgets                                                                                               |
| `pnpm test:e2e`                | Playwright tests on desktop and mobile against `dist/`                                                                                               |
| `pnpm check:contrast`          | Verifies WCAG contrast of the design tokens                                                                                                          |
| `pnpm check:links`             | Requests every external link in the content and reports broken ones (run before a release)                                                           |
| `pnpm illustrations`           | Redraws the project, hero and lab illustrations into `public/illustrations` from `scripts/illustrations` (`--sheet` writes a contact sheet)           |
| `pnpm images`                  | Regenerates AVIF/WebP variants from `assets-src/`                                                                                                    |
| `pnpm metrics`                 | Copies the latest GitHub and WakaTime figures from the profile repository into `src/content/shared/github-stats.json` (CI builds do it on their own) |
| `pnpm og`                      | Regenerates the Open Graph images and the Apple touch icon                                                                                           |
| `pnpm resumes`                 | Renders the resume PDFs and their previews from the OhMyCV sources in the `SebastianLopezO` repository; previews need poppler, or Docker to run it   |

## How it works

```
src/
  pages/                [...path].astro generates every page from lib/paths; 404.astro
  layouts/Page.astro    the document: head, role lock script, inlined styles
  islands/              PageIsland (one part of a page), the parts each island loads, the client renderer, the
                        build-time registry of every part and the head of each page
  views/                project, detail and 404 page bodies
  components/
    layout/             header, footer, language and role switchers
    sections/           one component per page section; below the hero each loads in its own chunk
    assistant/          launcher (an island) and lazy panel
    journey/            journey map, capability heatmap, focus radar and horizon (lazy chunk)
    case-study/         layered architecture diagram, figures and screenshots (lazy chunk)
    projects/           project card shared by the home section and the projects index
    page/               article parts shared by the project and detail pages: sections, page index, breadcrumb
    ui/                 form controls, carousel, toggle and the Lucide icons as static templates
  content/
    shared/             language-neutral facts: dates, tech, links, counts, role tags, projects, archive
    case-studies/       case study text in both languages (lazy chunk)
    project-pages/      text of the other project pages in both languages (lazy chunk)
    detail-pages/       text of the job, program, certification and organization pages (lazy chunk)
    en/, es/            localized text, checked against the Content type; startup.ts is what hydrates first
    roles.ts            section order, stack and priorities of each role view
  context/              language and role providers (accessors, so a role change updates in place)
  lib/                  paths, SEO head, sitemap, role ordering, formatting, assistant engine
  routes/               the location of a page and its links
  styles/               design tokens and global styles
scripts/                build and post-build, image, OG and resume generators, static server
nginx/                  production server config
e2e/, tests/            browser and build output tests
```

**Rendering.** `pnpm build` (`scripts/build.ts`) runs Astro, which renders the 182 pages (12 profile views, 2 project
indexes, 64 project pages, 8 detail indexes and 96 detail pages) and `404.html` with the CSS inlined, then
`scripts/postbuild.ts`, which writes `sitemap.xml`, `robots.txt`, `llms.txt` and the root's language redirect, hashes
each page's text into `page-dates.json` (a page keeps the `lastmod` the live site gave it until its text changes), and
pre-compresses everything with Brotli and gzip. Every page is one catch-all route, `src/pages/[...path].astro`, built
from the same parts: a part without a client directive is plain HTML that ships no JavaScript (the skip link, the
highlights, the footer, the WhatsApp button, the 404), and a part with one is a Solid island (`islands/PageIsland.tsx`)
that hydrates on its own. Like the earlier editions, nothing loads before the page has settled: the header, the hero,
the assistant's launcher, the body of a project or detail page and the part that loads the web fonts hydrate in the
first idle period after both the `load` event and the first paint (`client:settled`, `islands/settled.ts`), and each
home section then waits until it comes within 600 px of the screen. The pages are complete without JavaScript, and the
first paint uses fallback faces with matching metrics, so the web fonts' swap does not move the layout.

**Content.** Facts live once in `content/shared`; text lives in `content/en` and `content/es`. Collections are keyed
by id, so a missing translation is a type error, and a unit test fails if both languages drift apart. The years of
experience are computed from the first job (August 2022) at build time.

**Islands.** Each island wraps its part in what the single-page app gave the whole page once: the location, the
language with `content/{en,es}/startup.ts` (head, header, hero and figures) and the role view (`islands/shell.tsx`).
Its props are only the part's name, the language, the path and the view, so the page carries no serialized state. In
the browser an island's component and copy load in chunks of their own (`islands/parts.ts`, `content/sections.ts`)
before Solid hydrates it (`islands/client.ts` wraps Astro's Solid renderer for that), so every island hydrates in one
synchronous pass over its prerendered HTML. A section's chunk resolves only with the copy it reads
(`components/sections/section-loaders.ts`), so its components read the copy synchronously.
`<html data-hydrated="true">` appears once the islands of the first screen have hydrated, and each home section marks
itself the same way (`lib/ready.ts`).

**Projects.** Every project has its facts in `content/shared/projects.ts` (category, dates, stack, links, figures,
diagram and the archive organization that holds its repositories) and its card text in `content/{en,es}/projects.ts`.
Five of them are full case studies, with facts in `content/shared/case-studies.ts` and text in
`content/case-studies/{en,es}.ts`; the other twenty-seven pages take their text from `content/project-pages/{en,es}.ts`.
The slugs, and the projects each job links to, live in `content/shared/project-links.ts`. The project pages are
generated like the profile pages; their body is an island whose code and text load in chunks of their own
(`content/project-copy.ts`), with the head builders in `lib/seo-projects.ts`. Each page has its
own Open Graph image, generated by `pnpm og` (`case-*.jpg` for the case studies, `project-*.jpg` for the rest).

**Detail pages.** The jobs, programs, certifications and organizations reuse their facts in `content/shared` and the
home sections' text; what only their pages tell (positions, intros, areas, courses, issuers) lives in
`content/detail-pages/{en,es}.ts`, and the commits per organization in `content/shared/organization-activity.ts`.
`lib/details.ts` relates them (the projects of a job, the recommendations from it, the certifications earned while it
lasted, the jobs and programs going on when a certification was earned), so a page never states a link the facts do
not hold, and the timelines are built from the same facts. The slugs live in `content/shared/detail-links.ts`; the
pages render like the project pages (`views/DetailPages.tsx`, `islands/parts/detail-body.tsx`), with
their heads in `lib/seo-details.ts`. Every job, program, certification and organization has an Open
Graph image of its own (`experience-*.jpg`, `education-*.jpg`, `certifications-*.jpg`, `organizations-*.jpg`); a
certification's image shows the certificate when the page has a copy of it.

**Journey.** Milestones, capability levels, the radar and the GitHub activity per year live in
`content/shared/journey.ts`; planned dates and future levels are targets and are drawn dashed. The section is
prerendered with the page, and like every section its code and its text (`content/journey-copy.ts`) load in their own
chunk, so they do not count against the startup budget.

**Role lock.** The role comes from the URL path and the lock from `?locked=true`. An inline script marks the
document before the first paint so the switcher never flashes, and every internal link keeps the lock, also the links
of a section followed before it hydrates (`lib/lock.ts`). Nothing is stored in the browser.

## Migration from React

The edition came in two steps, each checked against the React build: SolidJS on the same Vite pipeline first, then Astro
with SolidJS islands. It keeps the React edition's markup, classes, content, routes and tests; the components were
ported one by one. Comparing the HTML of all 182 pages and the 404 element by element against the React build (ignoring
only Solid's `data-hk` keys, Astro's `<astro-island>` wrappers and scripts, generated ids and hashed asset names) finds
no difference in the head, the structured data, the text, the links or the attributes, and `page-dates.json` hashes
every page as before, so the sitemap keeps its dates. The unit, build and end-to-end suites pass in what they check; the
end-to-end tests scroll to a home section before using it, as a reader does, since it hydrates as it comes near. What
changed:

- **Rendering.** Astro generates the pages with Solid's server renderer, and only the islands hydrate. Solid's
  hydration is written for one root, so two steps before each island make it work island by island
  (`islands/client.ts`): its code and copy load first, because Solid keeps the nodes left to hydrate in one registry
  per page that each island's hydration starts afresh; and its hydration starts again, because Solid takes the first
  event it handles as the end of hydration and would otherwise render the islands that come later afresh. Astro's own
  `client:idle` starts loading while the page is still parsing; `client:settled` keeps the earlier editions' timing,
  after the `load` event and the first paint, so Lighthouse does not count the islands' scripts against the first paint.
- **Navigation.** Every page is its own document, so a role change, like any other link, loads the page of that view
  instead of re-rendering the open one; the role switcher sits in the hero, so the reader lands where they were. The
  locked view travels on every internal link, also before a section hydrates (`lib/lock.ts`), and the role view rides
  on the click that opens a project or detail page (`lib/role-links.ts`).
- **Reactivity.** Components run once and the providers hand out accessors, so the `?from=` view a project or detail
  page learns after hydration reaches every part that reads it, such as the way back, because they read it inside JSX.
- **Dependencies.** `react`, `react-dom`, `lucide-react` and `clsx` are gone: the 31 icons are static templates in
  `components/ui/icons.tsx` and `cn()` is a local helper. The runtime dependencies are `astro`, `@astrojs/solid-js`,
  `solid-js` and the three font packages; `eslint-plugin-solid` replaces the React hooks rules and Vitest runs a jsdom
  project and a Node project for the server render.
- **CSP.** Astro's island runtime, the `client:settled` directive and Solid's `HydrationScript` are inline scripts, each
  allowed by its hash (`nginx/security-headers.conf`).

Measured on the same content (`pnpm build`, gzip level 9; SolidJS + Vite is the first step, kept for reference):

| Measure                                              | React 19 | SolidJS + Vite | Astro + SolidJS |
|------------------------------------------------------|---------:|---------------:|----------------:|
| JavaScript before the first screen responds on `/en` |  91.3 KB |        39.8 KB |         36.7 KB |
| Every JavaScript chunk                               | 359.2 KB |       326.6 KB |        327.0 KB |
| First paint on `/en` (HTML up to the first section)  |  17.0 KB |        17.2 KB |         19.7 KB |
| Whole `/en` page                                     |  59.7 KB |        67.4 KB |         70.9 KB |
| Project page (`/en/projects/smartpot`)               |  23.2 KB |        24.6 KB |         27.2 KB |
| `node_modules`                                       |   523 MB |          56 MB |          320 MB |

On `/en` the islands of the first screen need 36.7 KB; each home section adds its own chunk only as the reader nears
it, where the earlier editions loaded and hydrated every section once the page had settled. The pages
grow because Solid marks every hydratable element with a `data-hk` key and Astro adds its island runtime (about 2 KB)
before the first island; the JavaScript that has to download, parse and run before the page responds is less than half
of what it was. `node_modules` grows again with Astro's compiler and its toolchain, which only the build uses. Part of
the saving is outside Solid: the hero's figures count the certifications and recommendations from
`content/shared/counts.ts` instead of importing both lists, which a test keeps in step.

The three production images were also compared side by side in Docker, each with the limits of `compose.yaml` (half a
CPU for nginx): Chromium on a phone screen with a 4× slower CPU, median of four alternating rounds of three loads, and
Lighthouse (mobile, median of five runs per page). Transfer sizes are Brotli.

| Measure                                                   |     React 19 | SolidJS + Vite | Astro + SolidJS |
|-----------------------------------------------------------|-------------:|---------------:|----------------:|
| Lighthouse performance (`/en` · `/es/backend` · SmartPot) | 92 · 92 · 93 |   88 · 93 · 95 |    99 · 98 · 96 |
| Lighthouse total blocking time on `/en`                   |       337 ms |         466 ms |          133 ms |
| First contentful paint on `/en`                           |       832 ms |         632 ms |          474 ms |
| JavaScript on `/en` before scrolling                      |     196.1 KB |       151.4 KB |         42.1 KB |
| JavaScript on `/en` after scrolling to the end            |     196.1 KB |       151.4 KB |        152.6 KB |
| Script time on `/en` before scrolling                     |      1002 ms |         174 ms |           40 ms |
| JavaScript heap on `/en`                                  |       6.1 MB |        6.24 MB |         2.59 MB |
| Site build inside the image (two builds)                  |  16.5–18.0 s |    19.9–30.2 s |     21.3–35.4 s |

Lighthouse scores accessibility, best practices and SEO at 100 on every page of the three. A project or detail page
loads its whole body as one island, so there Astro weighs what SolidJS + Vite did; the gain is on the home pages,
where the sections below the first screen load only as the reader reaches them.
